## 📖 サービス概要
MabaTalkは、発声や身体操作が困難で、まばたきによるYes/Noの反応のみで意思表示を行う方のための、「メッセージ確認 × 過去メッセージの振り返り」ができるコミュニケーション支援Webアプリです。

要介護者が最小限の負担で意思を示し、家族・介護スタッフが迷わず本人の気持ちや体調を理解・共有できることを目的としています。

## 📝 開発背景
- 妻の義父が脳卒中で倒れ、介護施設で寝たきりの状態となりました。
- 言葉を発することはほとんどできず、意思を伝える手段は「目を閉じる・開く」といったまばたきだけになります。
- 体調や要望を尋ねても、「暑い」「寒い」「痛い」といった変化をすぐに把握できず、表情だけでは判断が難しいため、もどかしさを感じる状況が続いていました。
- この状況を少しでも改善するため、本人が最小限の負担で意思を示せて、家族・介護スタッフが迷わず理解できるコミュニケーション手段を作りたいと考え、本サービスの開発を決めました。
- 本サービスを通して、家族・介護スタッフの負担を減らすだけでなく、本人が「伝えたい気持ち」や「生活の選択肢」を少しでも取り戻すきっかけになればと考えています。

## 📱 サービスの利用イメージ
1. 家族・介護スタッフがアプリを起動し、メッセージカテゴリを本人に見せます
2. 項目を順に指し示し、伝えたい内容があれば本人にまばたきしてもらいます
3. 家族・介護スタッフが項目を選択し、確認画面で「はい/いいえ」を本人に確認します
4. 「はい」が選択された内容が履歴として保存されます
5. 振り返りページで月ごとのグラフを確認したり、AI による傾向まとめを読んでケアに活かせます

未ログイン状態でも、メッセージの選択と意思表示の確認まで行うことができます。
ログイン時のみ、選択結果が履歴として保存されます。

## ⭐ サービスの差別化ポイント

既存の意思疎通手段は「本人が自ら操作できる」ことを前提としたものが多く、身体操作が困難な方への配慮が不十分です。

| 既存サービス | 課題 |
|------|------|
| 既存AACアプリ（単語カード型） | カードが小さく介護者が見せる用途に不向き。その場限りで記録が残らない |
| 五十音表アプリ | 本人による文字入力が前提 |
| 視線入力アプリ | 精度が低く実用に耐えない |
| 高性能視線入力端末 | 数百万円と高額で一般家庭では導入困難 |

MabaTalkはこれらの課題に対して以下の点で差別化しています。

- **介護者が見せる前提のUI**：大きなカード型表示で、寝たきりの方にも見やすい
- **カテゴリ構造による段階的確認**：介護者が本人の意思をスムーズに絞り込める
- **ログ記録とAI要約**：選択内容を蓄積し、本人の傾向や変化を後から把握できる
- **複数介護者間での情報共有**：異なるスタッフ間でもケア情報を引き継げる
- **無料・追加デバイス不要**：スマートフォン・タブレットのみで動作

### 技術選定の理由

**Ruby on Rails**：
設定より規約の思想で開発のセットアップ時間を最小化し、フロントエンドからバックエンドまで一貫して扱えるフルスタックフレームワーク。MVC・ルーティング・DB設計など必要な要素が整理されており、「この処理はなぜここに書くのか」という設計判断を実装とセットで身につけられる点を評価した。技術の幅を広げるよりRailsで設計力・実装力を深めてユーザーに価値を届けることを優先した判断。

**Hotwire（Turbo / Stimulus）**：
MabaTalkは介護現場での使用を想定しており、複雑なインタラクションより「シンプルで確実に動作するUI」を優先した。カテゴリ→項目→最終確認というステップ型のフローはHotwireのページ遷移ベースの設計と相性が良く、Rails 7のデフォルトとして公式採用されている点も評価した。

**PostgreSQL（Neon）**：
アプリケーション側だけでなくDB側でもデータの整合性を担保できることを重視し選定。カテゴリ→フローアイテム→ログという親子関係に対して外部キー制約が有効に機能する。NeonはサーバーレスDB設計のためスリープがなく、個人開発でも安定して動作し続ける点が決め手。

**Anthropic Claude Haiku**：
ログ要約という用途はHaikuの性能で十分であり、GPT系と比べてもコストを抑えられると判断。Constitutional AI（コンスティチューショナルAI）という原則ベースの学習アプローチにより誠実・安全な回答を重視して設計されている点が介護という文脈に適していると判断。AnthropicのRuby SDKが整備されておりRails環境への導入もスムーズだった。

**Render**：
個人開発フェーズではインフラ設定より機能開発・UX改善に集中することを優先し選定。AWSも検討したが、設定コストが現フェーズには過剰と判断した。GitHubとの自動デプロイ連携によりpushからデプロイまでのサイクルを短縮しており、今後ユーザー数が増えた場合はAWSへの移行も視野に入れている。
